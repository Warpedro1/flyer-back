# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a two-project monorepo for **Flyer**, an event-recommendation and social-gamification app. The two projects are independent git repositories with their own `.env`, dependencies, and tooling:

- `Flyer/` — React 18 + TypeScript + Vite frontend (Tailwind CSS v4).
- `FlyerBack/` — FastAPI (Python 3.11+) backend, talking to Supabase, OpenAI, and Pusher.

The conventions below are canonical for both projects.

## Language (decision 2026-10-17)

Everything the user sees is **Brazilian Portuguese (pt-BR)**: screens, API messages (`detail`), validation errors, e-mail templates, and LLM prompts whose output reaches the user. Never European Portuguese.
- Address the user as **você** ("seu/sua"), never "tu/teu/tua". Imperatives in the 3rd person ("Tente", "Aguarde", "Verifique", "Entre", "Escolha"); actions in progress in the gerund ("Carregando…", "Salvando…", "Enviando…"), never "A carregar…". Past tense without the accent ("Enviamos", "Não encontramos").
- Vocabulary: tela (not ecrã), usuário (not utilizador), compartilhar, ingresso (not bilhete), câmera, gerenciar, salvar (not guardar), registrar, atual, conexão, configurações, arquivo, equipe, "Meus eventos", "Algo deu errado".
- Guards: `Flyer/src/ptBR.test.ts` (app source without comments, plus `index.html` with `lang="pt-BR"`) and `FlyerBack/tests/test_pt_br.py` (string literals in `app/`, without docstrings, plus `supabase/templates/`). Code, comments, logs and docs for developers stay in English.

## Commands

### Frontend (`Flyer/`)
- `npm run dev` — Vite dev server on port 5173 (auto-opens browser).
- `npm run build` — type-check (`tsc -b`) then production build to `dist/`.
- `npm run lint` — ESLint over the project.
- `npm run test` — Vitest (jsdom). Run a single file: `npx vitest run src/pages/ChatPage.test.tsx`. Single test: add `-t "test name"`.
- `npm run test:ui` — Vitest UI runner.

### Backend (`FlyerBack/`)
- `uvicorn app.main:app --reload` — run the API locally (default `http://127.0.0.1:8000`).
- `pytest` — run tests (`asyncio_mode = auto`, `testpaths = tests`). Single file: `pytest tests/test_onboarding_pipeline.py`. Single test: `pytest tests/test_onboarding_guard.py::test_name`.
- Dependencies: `pip install -r requirements-dev.txt` inside `.venv`. `requirements.txt` is production-only (what Vercel installs into the function, under a 250 MB limit); the dev file adds `uvicorn` and `pytest`.

Health checks: `GET /` and `GET /health` (the latter echoes the active `CHAT_MODEL`).

## Backend architecture (`FlyerBack/app/`)

Strict layering — keep route handlers thin:
- `api/` — routers, one file per domain with a URL prefix: `chat` (`/chat`), `events` (`/events`), `plans` (`/plans`), `social` (`/social`), `trophies` (`/trophies`). All registered in `main.py`.
- `services/` — business logic and external integrations (`db_service.py`, `ai_service.py`, the `onboarding_*` pipeline, taste extraction, `error_log.py`).
- `models/schemas.py` — Pydantic v2 schemas.
- `core/` — `config.py` (pydantic-settings), `security.py` (JWT), `geo.py`, `limiter.py`.

Key cross-cutting patterns:
- **No ORM.** Supabase is accessed exclusively via the PostgREST REST API using `httpx`. A single shared `httpx.AsyncClient` is created in the FastAPI `lifespan` (`main.py`) and injected via `HttpClientDep` / `DbServiceDep` (`api/deps.py`) — never create per-request clients.
- **Auth.** `decode_access_token` (`core/security.py`) validates Supabase JWTs: ES256/RS256/EdDSA via JWKS first, falling back to HS256 with `SUPABASE_JWT_SECRET`. Routes get the user via the `get_current_user` / `get_current_user_with_token` dependencies.
- **Authorization lives in the backend, not in RLS** (issue #7, option B). Every PostgREST call runs with the `service_role` key — `DBService._user_headers` does not forward the user's JWT — so Row Level Security never applies on the API path. Clients have no privileges on `public` tables, sequences or functions (migration `20261009000000_revoke_client_table_access`): the publishable key only reaches Auth and Storage. The RLS policies stay in the schema but are unreachable today; do not count on them. New objects created by migrations no longer get `anon`/`authenticated` grants by default, and new functions are not granted to `PUBLIC` — `service_role` keeps its default grants. Never grant a `public` table or function to `anon`/`authenticated` without a design change. Consequences:
  - Any read or write of user-scoped data must filter by the `user_id` from the validated token, or go through `app/api/authz.py` (`require_owner`, `require_event_creator`, `require_media_paths_owned`, `require_place`, `require_trophy_icon`). Add new ownership rules there rather than re-implementing them per route.
  - Every route must depend on `get_current_user` / `get_current_user_with_token`. `tests/test_route_auth.py` walks the route table and fails otherwise; the only exceptions are the public list (`/`, `/health`, `*/health`, `GET /plans/`, `POST /auth/signup`) and `/admin/*`, which uses a shared secret instead: `X-Admin-Token`, or `X-Apify-Webhook-Secret` on the ingestion webhook.
  - `profiles.is_private` today only decides whether a follow starts as `pending`. The RLS also hides private users' events, trophies and profile data from non-followers, but the backend deliberately does not apply that (no UI sets `is_private` yet); revisit when privacy settings ship.
  - Never expose the service-role key to clients.
- **Async everywhere.** Use `async`/`await` and explicit return type annotations on all endpoints and service methods.
- **Pydantic.** Use `ConfigDict(extra="forbid")`. Money/score fields use `decimal.Decimal`; dates use `datetime`.
- **Rate limiting.** SlowAPI is wired globally in `main.py`; apply `@limiter.limit(...)` decorators to mutation endpoints (POST/PUT). Counters live in the shared store from `RATE_LIMIT_STORAGE_URI` (Upstash Redis; `REDIS_URL`/`KV_URL` also read) so limits hold across serverless instances; without it they fall back to per-instance memory. Requests with a valid token are counted per user, others per client IP (`x-forwarded-for`, which Vercel overwrites) — see `core/limiter.py`.
- **`SECURITY DEFINER` functions.** Revoke `EXECUTE` explicitly from `public`, `anon` and `authenticated`, then grant it to `service_role`. Supabase grants `anon` and `authenticated` through default privileges, separately from `PUBLIC`, so `REVOKE ... FROM PUBLIC` alone leaves the function callable at `/rest/v1/rpc/<name>` with the publishable key. Also pin `search_path`. Check with the Supabase security advisors after applying.
- **Catalogue (events and places).** `events` holds both: `kind = 'event'` (has a date, or was created in the app) and `kind = 'place'` (somewhere permanent to go: restaurant, gym, beach…, no date, `price_level` 1–4 and `opening_hours`). An event may point at its place (`place_id`). `category` is a slug from `EventCategory` in `models/schemas.py`, mirrored by `Flyer/src/utils/categories.ts`; renaming a slug needs a data migration. `price = 0` is free, `price = null` is unknown. Discovery filters (kind, category, date, distance, price) live in the `match_events` SQL function; places always pass the date and price filters.
- **Ingestion (`services/etl/`).** Apify actors defined in `etl/sources.py` (Google Maps places, Sympla events), each with a charge cap. `POST /admin/ingest` only starts the run (scraping outlasts a 60 s function), and only when the cap fits what is left of the month (decision 2026-10-19: `APIFY_MONTHLY_BUDGET_USD` = 5, or the account's own limit if lower, against Apify's `users/me/limits`; otherwise 409 `apify_budget_exhausted`). The GitHub workflow "Importar catálogo" (`.github/workflows/import-catalogue.yml`, secret `ADMIN_INGEST_TOKEN`) starts Sympla every Monday and Google Maps on the 2nd of each month, and simply skips when there are no credits; Apify calls `POST /admin/ingest/apify-webhook` when it ends, which loads the dataset: deterministic transform (`etl/transform.py`, `etl/taxonomy.py`, no LLM, coordinates only from the source), batched embeddings, upsert on `(source, source_event_id)`, contacts replaced and what changed moderated (see moderation), then event→place links, then (only with `KEYWORDS_ON_IMPORT`, on since 2026-10-18) keywords for stale rows with the time left (see the taste agent).
- **Trophies.** Every event gives a trophy at check-in. The creator may customise it in `EventCreate.trophy` (name, description, icon = an image they uploaded to `event-media`); a recurring event gets one `trophy_templates` row per occurrence. Without one, `POST /trophies/checkin` creates the default "Presença: <título>" on the first check-in (`trophy_templates.event_id` is unique, so concurrent check-ins share it). Icons are Storage paths, signed when read; a signing failure gives `icon_url = null`, never the raw path.
- **Check-in window** (`services/checkin_window.py`, decisions 2026-10-12). Events created in the app must have a start and an end (`event_date`, `ends_at`). Check-in opens at `checkin_opens_at` (the start by default, or the creator's scheduled time, or `POST /events/{id}/checkin/open`) and closes at `ends_at`, or earlier with `POST /events/{id}/checkin/close` (`checkin_closed_at`). Imported events open at the start and close at the source's end (start + 4 h when it has none). Places follow their opening hours in Recife time; no readable hours = always open. Times without a timezone are Recife time (`core/tz.py`, fixed UTC−03:00). Discovery hides an event only once it has ended, not when it starts.
- **How each event checks in** (`services/checkin_service.py:checkin_method`, decisions 2026-10-17), exposed as `EventRead.checkin_method`:
  - `qr`: events created in the app. Reading the attendee's QR at the door (`POST /events/{id}/attendance/scan`, creator only) **is** the check-in: window open, RSVP admissible, and the attendee's position. The ticket sends it in `POST /events/{id}/rsvp/qr`; the token carries it as claim `loc`, rounded to 4 decimals, with accuracy capped at 300 m and readings older than 2 min dropped. The limit is `CHECKIN_MAX_DISTANCE_METERS` + accuracy. Without a position the creator may resend with `confirm_without_location`; too far is refused.
  - Then `rsvp_admit`, the trophy (`award_checkin_trophy`, best effort) and the Pusher notice. Refusals use `ApiError` codes and never spend the `jti`.
  - `gps`: places, through `POST /trophies/checkin`.
  - `none`: imported events, which are only informative. No check-in or ticket (`ticket_unavailable`); the RSVP is the app's "Tenho interesse".
- **Realtime** (`services/realtime.py`, `api/realtime.py`, 2026-10-17). Pusher private channel `private-user-{id}`.
  - `POST /realtime/auth` signs only your own channel; `GET /realtime/config` gives the public key and cluster, or `enabled=false`.
  - Publishing uses Pusher's HTTP API through the shared `httpx` client and is best effort (2 s). Events: `checkin:done` `{event_id, trophy}`.
  - Payloads carry ids and trophy names only, never personal data. The app polls as a fallback.
- **Meus eventos** (#40, decisions 2026-10-17). `GET /events/mine?role=created|going|all&when=upcoming|past&limit&offset`: without parameters, what you created, newest first (as before). `going` = your RSVP `confirmed`, `waitlisted`, `called` or `admitted` (never `cancelled`/`no_show`), with `EventRead.my_rsvp` `{status, waitlist_position}`; `all` merges both, each event once. `when` splits at the end of the event (`ends_at`, or the start + 4 h without one), soonest first for upcoming and latest first for past. Places never come: their check-ins are trophies, and `TrophyRead.event_id` links the trophy to its event or place.
- **Editing.** `GET /events/{id}/edit` and `PUT /events/{id}`: creator only, everything but the recurrence (a series is edited one date at a time); imported events and places are not editable. `PUT` replaces the media and always upserts the trophy (the default name follows a new title).
- **Login by e-mail and the second factor** (decisions 2026-10-12). Besides Google, accounts with e-mail and password (Supabase Auth: sign-up confirmed and password reset by 6-digit codes e-mailed by Supabase, never one-time links: e-mail scanners open links and spend them, #43). A session opened with a password (`amr` has `password`) only reaches the API after the 6-digit code Supabase e-mails to the account: `deps._authenticated_payload` answers 403 `email_code_required` until `POST /auth/email-code/verify` records its `session_id` in `login_second_factor` (backend-only table). Google, confirmation and recovery sessions pass. The `/auth/email-code/*` routes use `get_current_user_pending_code` (token only); nowhere else may. The code always goes to the e-mail in the token.
- **CPF and phone** (decisions 2026-10-12; phone optional since #29, 2026-10-17). Every account has a CPF; the Brazilian mobile is optional. Both are unique when present (`profiles.cpf`, `profiles.phone` in E.164 or null; unique indexes, the phone one partial, and `is_valid_cpf` check in the database too); a phone given is still validated. Sign-up by e-mail goes through the backend, `POST /auth/signup` (public, rate limited): it validates (`core/br_documents.py`), says plainly which of e-mail/CPF/phone is taken, then creates the user in Supabase Auth with them in the metadata (the `handle_new_user` trigger copies them). Accounts without a CPF (Google) get 403 `profile_incomplete` everywhere until `PUT /auth/profile/identity` (CPF, phone optional); the `/auth/profile/*` routes use `get_current_user_pending_profile`. CPF and phone are only ever returned to their owner, masked (`GET /auth/profile/status`); never add them to `ProfileBrief`/`UserRead`.
- **Sign-up code tied to its browser** (decisions 2026-10-14). The sign-up e-mail carries only the 6-digit code (template "Confirm signup", no link). Supabase codes can be redeemed with the publishable key, so the code alone must not open the account (a mistyped e-mail would hand someone else an account with your CPF): `POST /auth/signup` answers a secret `ticket` (only its sha256 is stored, in `signup_tickets`), the profile starts `signup_pending` (trigger, `flyer_signup` in the metadata), and `deps._authenticated_payload` answers 403 `signup_pending` until `POST /auth/signup/activate` gets that ticket from a session of the same account. The app keeps the ticket in `localStorage` (any tab of that browser, 24 h; not another device or browser, and not tied to the IP). A sign-up whose e-mail/CPF/phone only clash with pending accounts deletes them and goes on; only active accounts give 409. `POST /auth/signup/activate` uses `get_current_user_pending_profile`, like `/auth/profile/*`.
- **Onboarding pipeline.** `onboarding_pipeline.py` orchestrates guard (heuristics → moderation → LLM judge) → taste agent → embeddings → taste docs (`user_taste_documents`, pgvector) → profile. Moderation uses `MODERATION_MODEL` (`omni-moderation-latest`; `text-moderation-latest` was shut down on 2025-10-27, #26). Each step has its own limit, retries included (`MODERATION_TIMEOUT_SECONDS`, `GUARD_JUDGE_TIMEOUT_SECONDS`, `TASTE_EXTRACT_TIMEOUT_SECONDS`, `TASTE_SYNTH_TIMEOUT_SECONDS`, `EMBEDDING_TIMEOUT_SECONDS`), and their sum stays under `ONBOARDING_BUDGET_SECONDS` (50 s, inside the 60 s of a Vercel function; `tests/test_onboarding_budget.py`). Moderation down is 503 `moderation_unavailable`; a slow judge, analyst or synthesizer lets the onboarding go on (moderation already passed). Profile reads/writes that fail are 500 `profile_write_failed`.
- **Taste agent** (`services/taste_agent.py`, #31, #26 part 2, #22 part B; decisions 2026-10-18). Turns what a person wrote, or an event says, into pt-BR keywords plus a 1–2 sentence summary, and **the vectors are made from those, never from the raw text**, so people and events are compared in the same terms.
  - Model `TASTE_EXTRACTOR_MODEL` (`gpt-4o-mini`), through `with_structured_output`; prompts in pt-BR, the user's text goes inside tags as data.
  - Person: one analyst call per answer, all at once (items cited: kind, genre, era, themes, audience, what it says about the person), then a synthesizer → 15–30 keywords. The person's vector is `person_embedding_text` (keywords + summary); stored in `profiles.interest_keywords`/`interest_summary`, the analysis in `user_taste_documents.analysis` (the chat's documents keep the answer). Fallbacks: a failed analyst leaves that answer raw (`extraction: short`), a failed synthesizer is replaced by a deterministic merge, nothing analysed = the raw answers make the vector and the keywords are cleared. `ensure_interest_embedding` rebuilds from the stored keywords first.
  - Event or place: one call → 8–15 keywords; vector = title + category label + keywords + summary (`event_embedding_text`, no description). `events.keywords`, `keywords_summary`, `keywords_hash` (md5 of title, description, category: `event_content_hash`, the same expression as the generated column `keywords_stale`; change both together). Create/PUT run it in the request (`services/event_keywords.py:embed_app_events`, once per series; a PUT that kept the text of a fresh row redoes nothing); the import reuses fresh keywords and leaves the rest stale; `POST /admin/events/keywords` (X-Admin-Token) **estimates the cost by default** (`dry_run`) and otherwise works through at most 100 stale rows (one embedding batch) inside 60 s: call again until `remaining` is 0. Invariant: a row whose keywords are fresh (`keywords_stale = false`) has the vector made from them, because the reprocessing only reads stale rows. So keywords are only written together with that vector, the import stops if it cannot read the stored keywords, and a batch whose embeddings failed is upserted without `event_embedding` (it keeps the old one); any other failure leaves the row stale.
  - Failures go to `app_errors` (`taste_agent_error`/`taste_agent_timeout`, `details.stage`), once per batch in the import. Tests never reach OpenAI: an autouse fixture makes `taste_agent._structured` fail, so every caller takes its fallback; stub it to test the agent. Reference examples in `tests/fixtures/taste_agent/`, checked against the real API only with `RUN_LIVE_LLM_TESTS=1`.
  - Not yet in keyword space: `POST /chat/sync` still blends a vector of the raw chat text into the person's (12% at first, then 30%).
- **Moderation and personal data** (`services/moderation.py`, `core/personal_data.py`, #22 part A; decisions 2026-10-18). OpenAI's moderation (`MODERATION_MODEL`) checks texts and photos; videos cannot be checked and pass.
  - Created or edited in the app (`check_event_content`, before anything is written): title, description, place, trophy name/description and every image (photos and trophy icon, signed for 2 min). A refusal is 422 `content_blocked` naming the field and the reason in pt-BR; an e-mail, phone (with or without the area code or +55, Unicode dashes included; without the area code only a mobile written with its separators, "99999-8888" or "9 9999-8888"; two years such as "Sub-17 2025-2026" are not a phone unless the area code is in parentheses) or valid CPF in those texts is 422 `personal_data`; moderation down (or Storage failing to sign the photos, recorded as `storage_sign_error`) is 503 `moderation_unavailable`, never a pass; a photo or icon whose file no longer exists is 422 ("não está mais disponível"). Event media must be the creator's own Storage paths: external URLs are refused (422).
  - Imported: contacts become "[contato removido]" before anything is hashed; what is new or changed since its last check (`events.moderation_hash` vs the generated `moderation_stale`, md5 of title, description and cover: `event_moderation_hash`, change both together) is checked within `IMPORT_MODERATION_BUDGET_SECONDS` (texts 32 per request, 4 requests at a time; a request that fails or runs out of time leaves only its own items unchecked). Refused text never enters (a row already here is hidden: `moderation_blocked`); a refused or unreadable cover is dropped and remembered (`moderation_dropped_cover`, its reasons or `unreadable_cover` in `moderation_reasons`), so the next import, which still brings it, does not check it again; an unreadable one is tried again after `UNREADABLE_COVER_RETRY_DAYS` (7); what could not be checked waits for the next import (an existing row keeps its checked content). Unchanged rows are never checked again; hidden rows always are (their source may go back to content that was allowed).
  - Hidden rows (`moderation_blocked`) are left out of `match_events`, a place's events, "Meus eventos" (`going`), event→place links, RSVPs, tickets and the GPS check-in (404), and get no keywords. `GET /events/{id}` is 404 too, except for the creator of an app event, who gets it with `EventRead.moderation_blocked = true` and a notice in the app to edit it (saving checks it again and shows it). The rows that were here before #22 A are checked by `POST /admin/events/moderation` (X-Admin-Token, free, ≤100 per call): imported rows by text and cover, app rows as saving them would (place, trophy, photos and icon; a photo the moderation cannot read, or whose file no longer exists, hides it too), never rewritten (contacts the creator wrote before #22 A are left as they are); `scripts/reprocess_catalogue.sh` runs it and then the keyword reprocessing, either on the owner's machine (token typed there) or from GitHub with the manual workflow "Reprocessar catálogo" (`.github/workflows/reprocess-catalogue.yml`, secret `ADMIN_INGEST_TOKEN` in the repository's Actions secrets); the token is never sent to anyone.
  - Tests never reach the moderation: an autouse fixture allows everything at `ai_service.moderate_inputs` and skips signing (`moderation.path_verdicts`); set them to test a refusal.
- **"Melhorar descrição"** (`POST /events/describe`, `services/event_describe.py`, #22 part C; decisions 2026-10-18). Free for everybody, `10/hour` per person. `DESCRIBE_MODEL` (`gpt-4o-mini`) rewrites the creator's own title/description in pt-BR without inventing facts (dates, prices, addresses, contacts), ≤2000 characters; the input follows the same personal-data rule as saving, input and suggestion go through the moderation, and nothing is saved (`EventDescribeRead {description}`). Failures are 503 `describe_unavailable`. In the app the button sits under the description in `EventForm`; the suggestion replaces the text only with "Usar" ("Manter meu texto" drops it).
- **Errors and observability** (#30, #25 phase 1, decisions 2026-10-16). `core/request_context.py`: every response carries `X-Request-Id` (exposed by CORS); `RequestContextMiddleware` sits inside `CORSMiddleware` and turns any unhandled exception into a JSON 500 `{"detail", "code": "internal_error", "request_id"}` *with* the CORS headers (Starlette's own `Exception` handler runs outside every middleware). Raise `core/errors.py:ApiError(status, code, message)` for errors the app must recognise; it answers `{"detail": message, "code", "request_id"}` (`detail` stays a string). 429s have the same shape (`rate_limited`). A request with no bearer token is 401 `not_authenticated` (`deps._BearerToken`, with `WWW-Authenticate: Bearer`), never FastAPI's English 403. A 422 keeps FastAPI's `detail` list but each item is only `{loc, msg, type}` with `msg` in pt-BR (`core/validation_messages.py`, #42), plus `code: "validation_error"` and `request_id`; Pydantic's `input` is dropped because it echoes passwords and CPFs. Every 5xx (unhandled, `ApiError` or `HTTPException`), AI failure (moderation, judge) and error reported by the app (`POST /telemetry/client-error`, sessions only) is written to `app_errors` through `services/error_log.py`: best effort (never raises, 2 s), kept 30 days (trigger on insert), backend-only table. Logs are JSON lines (`core/log_config.py`) with `request_id` and `user_hash`. Never put a raw user id, e-mail, CPF or phone in a log or error record: the user is `hash_user_id` (sha256, 16 hex) and texts go through `core/log_scrub.py:scrub`; `httpx` request logging stays at WARNING because PostgREST URLs carry those filters. With `LANGSMITH_TRACING`, every OpenAI call of `ai_service` is traced (`wrap_openai`), text included.
- **Public profile.** `ProfileBrief` (what one user sees of another: followers, requests, attendees, the scanner) is `{id, name}`. Never add the e-mail (#30); the public @username and nickname come with #32.

## Frontend architecture (`Flyer/src/`)

- **Routing** in `App.tsx`: `/login` is standalone; all other pages render inside `AppLayout` (sidebar on desktop, bottom-nav on mobile).
- **API access.** All backend calls go through `services/flyerApi.ts`, which uses the pre-configured Axios instance in `lib/apiClient.ts`. The request interceptor pulls the Supabase session and injects `Bearer <access_token>`. Note: the response interceptor deliberately does **not** sign out on 401 (a backend JWT-check failure should not eject a user with a valid Supabase session).
- **Auth/state.** Supabase (`lib/supabase.ts` + `@supabase/supabase-js`) manages session/JWT, exposed through `contexts/AuthProvider.tsx` + `hooks/useAuth.ts`. No global state library (Redux/Zustand/etc.) — this is prohibited.
- **Errors** (#30, #33). `utils/apiError.ts`: `getApiErrorInfo` reads `detail`, `code`, `request_id` (or the `X-Request-Id` header); `formatApiError` shows 5xx as "… (código: X · ref Y)", FastAPI validation as "Dados inválidos: …", no response as a connection message; `isNotFoundError` for 404. `components/errors/ErrorBoundary.tsx` is the only class component (React has no hook for error boundaries): it wraps the whole app (`main.tsx`) and the layout's `<Outlet>` (keyed by path, so navigating clears it), shows "Algo deu errado" with a ref and reports to `POST /telemetry/client-error` (that ref as `X-Request-Id`; only with a session). Unknown routes render `NotFoundPage`; a 404 from the API renders `NotFoundContent` inside the page. A JS chunk that no longer exists after a deploy reloads the page once (`utils/chunkReload.ts`, also on `vite:preloadError`). A session whose account is gone gets 401 `session_invalid`: sign out and go to `/login`. A request sent with no session gets 401 `not_authenticated` and the interceptor goes to `/login` (`lib/emailCodeRedirect.ts`, outside the entry screens).
- **Types.** `types/index.ts` must mirror the backend Pydantic schemas exactly. Decimal fields (money, ratings) are typed as `string | null` on the UI side.
- **Styling.** Tailwind CSS v4 only (via `@tailwindcss/vite`). Do not add Bootstrap, MUI, or any prebuilt component library. Accent color is `red-600`; prefer `rounded-2xl`/`rounded-3xl`. Root container is `h-screen overflow-hidden`; only `<main>` scrolls (`overflow-y-auto`).

### Frontend conventions
- **TDD:** write/update the `*.test.tsx` (or `*.test.ts`) file before changing a component or hook.
- Tests use Vitest + `@testing-library/react` + `userEvent`. Test behavior, not internal state. **Never make real API calls** — intercept with MSW (`src/mocks/handlers.ts`, `src/mocks/server.ts`).
- TypeScript strict mode; `any` is forbidden. Functional components only, `PascalCase` filenames. Always write `useEffect` cleanup functions for listeners/timeouts/subscriptions.

## Environment

Both projects require their own `.env` (copy from each `.env.example`). The frontend needs at least `VITE_API_BASE_URL` (`apiClient.ts` throws on startup if missing) plus Supabase keys. The backend needs `SUPABASE_URL`, `SUPABASE_KEY` (a `sb_secret_...` key, or the legacy `service_role` JWT until Supabase retires it at the end of 2026), `SUPABASE_JWT_SECRET`, and optionally `OPENAI_API_KEY`/`OPENAI_KEY`, Pusher (`PUSHER_*`), `CHAT_MODEL`, and `EMBEDDING_MODEL`. SQL migrations live in `FlyerBack/supabase/migrations/` (timestamped, applied in order); `FlyerBack/migrations/003_create_plans.sql` is legacy.
